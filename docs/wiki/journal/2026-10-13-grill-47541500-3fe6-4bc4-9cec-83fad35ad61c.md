## Question 10

```text
Round: Library dependencies — versions, customization and setup
Question: Should each library have its own pinned version and manual upgrade?
Description (Markdown source):
Libraries are now selected as dependencies. A pinned engine alone does not stop a library from changing a site's rendering or editable fields. Library versions can be selected independently of the engine version.
Recommendation: Pin each library and upgrade it deliberately, with verification and maintainer-owned migration when necessary. A content-only publication should use the same implementations as before.
Options: Pin libraries; upgrade them manually / Fetch the latest library code whenever the site builds
Selected: Pin libraries; upgrade them manually
```

## Question 11

```text
Round: Library dependencies — versions, customization and setup
Question: Where should a site's library sources and revision settings be declared?
Description (Markdown source):
Subscriptions remain outside the admin portal. Committed project configuration makes the intended libraries visible to local development, code review and builds. Environment-only settings let hosts choose libraries without a Git change, but the repo alone no longer describes the build inputs.
Recommendation: Commit dependency sources and revision settings with the site. Use environment configuration for credentials and deployment-specific values, without silently replacing library selections.
Options: Committed project configuration / Launch/environment configuration only / Committed defaults with environment overrides
Selected: Committed project configuration
Notes: 
```

## Question 12

```text
Round: Library dependencies — versions, customization and setup
Question: How should a site customize a library implementation beyond its exposed settings?
Description (Markdown source):
Ordinary field and layout settings continue to use the shared dependency. This question concerns changing its actual source code. A separate local copy becomes site-owned; patches retain the upstream relationship but can conflict when the library changes.
Recommendation: Allow an explicit developer-created local copy with a distinct identity. The site owns its future changes; existing content switches to it deliberately. No automatic merging of library updates is promised.
Options: Copy locally as a separately identified site extension / Apply site-local patches to the library implementation / Keep library code unchanged; request deeper changes upstream
Selected: Keep library code unchanged; request deeper changes upstream
Notes: 
```

## Question 13

```text
Round: Library dependencies — versions, customization and setup
Question: Which layout should Factory reset use when the engine no longer includes Starter?
Description (Markdown source):
Today reset creates one active Starter layout. The new engine will bundle no site layouts, and the site must still have at least one active layout. Its starting design must therefore come from site-owned code or an installed library.
Recommendation: Let the developer declare the site's initial layout in project configuration. Reset uses that installed design and its defaults, giving each site a predictable starting point.
Options: Use a developer-configured initial layout / Ask the admin to choose an installed design during reset
Selected: Use a developer-configured initial layout
Notes: 
```
