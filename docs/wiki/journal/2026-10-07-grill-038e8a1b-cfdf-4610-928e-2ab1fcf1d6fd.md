## Question 93

```text
Round: Content model · reopening nested objects and lists
Question: How much nesting should owned objects and lists support?
Description (Markdown source):
The current agreement permits only one level: an entry can own an object or a list of rows, but those groups cannot contain another object or list. This question reopens DEC-111 and the depth portion of DEC-119.

For example, a Product could own specification groups, and each group could own specification rows. That needs two levels. An object inside each specification row would be a third level. A list and its row wrapper count as one level; the entry itself does not count. Reusing a named definition adds no extra level beyond the object or list that uses it.

Keeping one level makes implementation simpler, but the example would need flattening or separate collections and relation selection. Three levels allow common nested structures while keeping an explicit boundary, but require nested validation, editing and bindings. No fixed cap allows any finite depth, with more complex authoring and additional engineering limits on processing and content size.

This choice applies equally to named and inline structures. One shape per list, one target collection per relation, and dedicated navigation for nested editing remain agreed. Reference traversal is separate from owned nesting. Recursive reusable definitions and exact safety mechanics can be considered after this choice.
Recommendation: Allow up to three owned levels. This handles the specification example and an additional inner group, while retaining a clear limit. Three is a proposed practical starting point, not a measured technical maximum.
Options: Allow up to three owned object/list levels / Keep the current one-level limit / Allow any finite nesting depth; no fixed product cap
Selected: Allow up to three owned object/list levels
```
