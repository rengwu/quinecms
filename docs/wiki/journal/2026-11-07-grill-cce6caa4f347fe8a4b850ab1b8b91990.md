```text
Round: Admin redesign: structure, editor and visual system
Question: How should the admin shell be structured?
Description (Markdown source):
Save draft and Publish act on the whole site, not on one document, so they need a place that stays visible on every screen. A top bar provides it. ## Question 8
```

```text
Round: Admin redesign: structure, editor and visual system
Question: Try the preview prototype. Which modes should the editor offer?
Description (Markdown source):
**Is it feasible? Yes, and it fits how the preview already works.** The live preview renders inside the editor page, not in an iframe. The Archline, Intr and Tessera designs respond to container queries, not viewport media queries. So the preview can render at a fixed width (1280px for desktop, 390px for mobile) and be scaled to any size with a CSS transform. This prototype works the same way.

- Switching modes changes only the CSS of a single preview element, so interactive blocks (React, Vue and Svelte islands) stay mounted.
- The floating window keeps the device's aspect ratio as you resize it from any corner, and you can drag it anywhere in the workspace.
- A scaled frame also contains `position: fixed` elements such as sticky headers, which suits a preview.
- Limit: viewport units and `@media` width queries still read the browser window. The library uses `100dvh` once.
- Not proposed: a separate always-on-top OS window (Document Picture-in-Picture), which works only in Chrome and Edge.

In the prototype: type in **Heading**, drag the divider, switch to **Float**, drag the window by its bar, resize it from any corner, switch Desktop and Mobile, and toggle the sidebar with the top-left button.
Recommendation: All three: Off, Split and Float.
Options: Split view / Floating window / Off
Selected: Split view / Floating window / Off
Notes: i don't really  like the location of the preview selector [Image #1: evidence/2026-11-07-admin-redesign/preview-selector.png]. is there a better place for that?
Status: feedback
```

## Question 15

```text
Round: Admin redesign: structure, editor and visual system
Question: What should the components be built on?
Description (Markdown source):
Kumo is Cloudflare's styling on top of Base UI. Its control heights are fixed in Tailwind classes at 20, 26, 36 and 40px. The editor overrides it with 15 `!important` rules, and a build step scopes Kumo's stylesheet to `.kumo-ui`.

The editor uses 14 Kumo pieces: Badge, Button, Checkbox, Dialog, Input, InputArea, Label, Link, Radio, Select, Switch, Table, Tabs and Toast. Base UI 1.8 is already installed with Kumo and provides their behaviour and accessibility. Thin components of our own, with our tokens, would remove the overrides, the scoping step and Kumo's Tailwind stylesheet. The gallery would show each one in all its states. Keeping Kumo costs less at first, but every visual change keeps fighting its classes.
Recommendation: Our own components on Base UI.
Options: Our own components on Base UI / Kumo at its small size, re-themed
Selected: Our own components on Base UI
```
