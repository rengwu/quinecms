The maintainer's preceding instruction establishes that the map contains CMS
capabilities, while Kahf, chartr, Quine and similar recreations are testing trials.

| Question | Submitted choice |
| --- | --- |
| Q1. Should the map cover developer-facing CMS capabilities too? | Include editor, public-site and developer capabilities |
| Q2. How much detail should the feature map itself expose? | Grouped capabilities with concrete subfeatures |
| Q3. Where should the recreation trials be discoverable? | A separate Trials area |
| Q4. How much verification detail belongs on an individual feature page? | Behavior contracts with links to separate checks and evidence |
| Q5. How far should the documentation cleanup go? | Audit and reorganize all current feature documentation |

The recommendations distinguish engine/CLI functionality from working methods;
group concrete functionality without creating a page for every control; link a
Trials index from the wiki home; retain current behavior, entry points and limits
on feature pages; and audit current source while preserving historical evidence.

See the [accepted scope and cleanup plan](../discussions/feature-map-scope.md) and
DEC-252–DEC-257 in [Decisions](../decisions/index.md). There are no unanswered
items. This is interview evidence, not a completed documentation audit or product
verification result.
