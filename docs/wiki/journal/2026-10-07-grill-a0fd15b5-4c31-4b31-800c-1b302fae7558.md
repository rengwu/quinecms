## Question 86

```text
Round: Collections & schemas · shape and behavior
Question: May shallow objects and list rows contain relation fields?
Description (Markdown source):
You chose one level of objects/lists. A top-level Address object or a list of FAQ rows fits that limit; another owned object or list inside those groups would not.

The remaining boundary is **references**. A Project's Credits list could have a Person relation and a Role text field in each row. An object could also contain a relation configured for multiple entries. Those fields store links, not embedded copies of the target's fields.

Allowing these relation fields would preserve flat owned groups while connecting them to shared entries. The alternative keeps all relations at the entry's top level. This choice covers both single and multiple references.
Recommendation: Allow relation fields inside shallow objects and list rows. Keep further owned objects/lists disallowed inside those groups.
Options: Allow relations at the top level and inside flat groups / Keep relation fields at the entry's top level only
Selected: Allow relations at the top level and inside flat groups
```

## Question 87

```text
Round: Collections & schemas · shape and behavior
Question: Should editors control the order of entries selected by a multiple-relation field?
Description (Markdown source):
A Featured Articles field may need a particular lead article first. A Co-authors field may need a deliberate credit order.

With editorial ordering, editors can reorder selected entries and templates receive that stored order. With automatic ordering, the site sorts the selection consistently, such as by title, and editors cannot give it a custom sequence.

This concerns an explicitly selected list of entries. An automatically queried list such as Latest Articles is a separate feature.
Recommendation: Let editors reorder selected entries and preserve that order when rendering.
Options: Editors control the stored order / Use automatic ordering only
Selected: Editors control the stored order

```

## Question 88

```text
Round: Collections & schemas · shape and behavior
Question: Can the same entry appear more than once in one multiple-relation field?
Description (Markdown source):
A Featured Articles selection could accidentally include the same article twice, producing repeated cards. Some presentations may intentionally repeat content.

Preventing duplicates means a target already selected cannot be selected again in that field. It can still be used in other fields and other entries. This does not prohibit separate credit rows or association records from referring to the same Person for different purposes.
Recommendation: Prevent duplicate targets within a direct relation field. Keep intentional repeated associations explicit.
Options: Select each target once per relation field / Allow the same target multiple times
Selected: Select each target once per relation field

```

## Question 89

```text
Round: Collections & schemas · shape and behavior
Question: If a single-entry collection has a public page, how should its URL work?
Description (Markdown source):
A Company Profile may remain data-only, or render through a generic page. For the routed case, a direct path would give it one URL such as **/about**. The ordinary collection formula would instead use a prefix and entry slug, such as **/company/profile**.

A direct path would be an explicit exception for single-entry mode. Ordinary collections would keep prefix plus slug, and all public paths would still need to avoid collisions. No page is generated unless a generic page is assigned.
Recommendation: Use one explicit path for a routed single-entry collection, without a separate entry slug.
Options: One explicit path, such as /about / Collection prefix plus entry slug, such as /company/profile
Selected: One explicit path, such as /about
```
