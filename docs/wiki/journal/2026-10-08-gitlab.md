# GitLab repository support

The user asks to make the sitebuilder GitLab-compatible alongside GitHub, after
clarifying that each client instance targets its own repository and that hosting
instructions should be platform agnostic. DEC-135 records that scope.

The editor now selects GitHub or GitLab in Connection. GitLab supports its default
public instance or a configured HTTPS self-managed URL and nested namespaces.
Neutral build variables prefill the connection; GitHub's existing owner/repository
variables remain fallbacks for that provider. A small `RepositoryStore` interface
shares load/save/publish contracts and pure validation helpers. GitHub retains its
existing tree/commit/ref implementation; GitLab uses browser fetch without a new
SDK, application server or remote-agent layer.

The main integration difference is preserving exact snapshots. GitLab's public
API does not offer the same non-forced ref update as GitHub. The implementation
creates a unique temporary branch for each save/publication, then advances the
target through a SHA-pinned fast-forward merge request. Save creates one content
commit; Publish reuses the saved commit and leaves newer drafts intact. The project
needs fast-forward merging and optional/disabled squashing. The adapter checks
those settings but does not change them, force updates, bypass review/pipeline
requirements or schedule delayed auto-merges. Merge requests remain as provider
history; successful merges request source-branch removal. Interrupted operations
may leave temporary branches or requests for manual cleanup.

Publishing from the editor was stated as the engineering default after an optional
workflow question received no answer. A separate human-reviewed publication mode
was not selected. This distinction is recorded rather than attributing that exact
workflow choice to the user. API references and operational details are in the
[publishing contract](../features/publishing.md).

Credential recovery is now tied to provider, instance, namespace/repository and
branch. Editing the destination clears the token, and Lock clears retained Git
credentials. Backups retain repository identity without credentials. Existing
GitHub sessions may need to re-enter their token after this change.

Browser verification exposed a pre-existing first-connection issue: converting
the bundled legacy layout record made an untouched site appear dirty. Comparing
the editor state against the same normalized baseline fixes that false warning
for both providers; a mounted regression covers it.

The [verification record](../verification/runs/2026-10-08-gitlab.md) distinguishes
mocked transaction tests, actual browser checks and live-provider limits. No
credentials were supplied to GitLab/GitHub, and no remote repository, project
setting or deployment was changed. Concurrent admin-theme, heading and usage
work and the prior local-authoring increment were preserved.
