## Question 90

```text
Round: Collections & schemas · using the model
Question: Should templates be able to list entries that reference the current entry?
Description (Markdown source):
An Article stores its Author relation. On that Author's page, we could derive **all Articles that reference this Author**, without making editors maintain a second Articles list on the Author.

The result would be read-only derived data for the template; editors change the original Article.author field to change membership. This differs from a manually curated, ordered selection.

Incoming-reference lookup is already needed to block deletion while an entry is used. This choice adds its use in public presentation, such as author articles, category contents or projects involving a person.
Recommendation: Support derived reverse lists in templates. One stored relationship can then serve both sides of the site without duplicated maintenance.
Options: Support derived reverse lists in templates / Use reverse lookups for admin usage checks only
Selected: Something else
Notes: no opinion, choose the leanest, simplest option
```

## Question 91

```text
Round: Collections & schemas · using the model
Question: Should editors be able to create or edit a linked entry from a relation control?
Description (Markdown source):
While editing an Article, an editor may need to correct an Author's biography or create a new Author before selecting it.

Integrated authoring would open a dedicated editing level, then return to the Article with its unsaved work preserved. Editing the Author changes shared content used by other entries; it still follows the site's normal draft/save/publish workflow.

The simpler alternative makes the relation control selection-only. Editors would visit the target collection separately to create or edit its entries. Neither option puts a nested editor inline among parent controls.
Recommendation: Allow creation and editing from relation controls through dedicated navigation levels, preserving the parent draft.
Options: Create and edit targets from relation controls / Select existing targets only; edit them separately
Selected: Something else
Notes: no opinion, choose the leanest, simplest option
```

Round: Collections & schemas · using the model
Question: Where should collection schemas and reusable object definitions be managed?
Description (Markdown source):
Collection schemas already have their own area, separate from Content. Reusable object definitions now need a home too.

**One Schemas area:** rename Collection schemas to Schemas, with separate Collections and Objects destinations inside it.

**Separate areas:** retain Collection schemas and add an Object types area alongside it.

Content would continue to contain actual entries. Object definitions would contain fields, not shared content values. This navigation choice does not introduce shared whole-entry schemas, which you already declined. Individual definitions and fields would still open dedicated navigation levels.
Recommendation: Use one Schemas area with separate Collections and Objects destinations. It groups structure editing while keeping entry editing in Content.
Options: One Schemas area with Collections and Objects / Separate Collection schemas and Object types areas
