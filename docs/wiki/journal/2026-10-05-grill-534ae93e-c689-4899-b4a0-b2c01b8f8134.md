## Question 33

```text
Round: QuineCMS — content and block contracts
Question: Who should produce and maintain the shared vendor files?
Context: Your registered, statically hosted vendor idea can be implemented by the build: one compatible dependency set produces minified shared modules on the site's own host. Blocks import the same URLs. A manually maintained vendor folder/import map offers direct control but also needs dependency and browser-module compatibility maintenance. Your example version numbers will not be treated as pins.
Recommendation: Let the build generate self-hosted vendor/shared modules from the registry and lockfile. Validate compatible versions and inspect the output for duplication; load only dependencies needed by the current page.
Options: Build-generated, self-hosted vendor modules / Explicitly maintained vendor files and import maps
Selected: Build-generated, self-hosted vendor modules
Notes: 
```

## Question 34

```text
Round: QuineCMS — content and block contracts
Question: Should a document's filename follow its permanent ID or its public URL?
Context: For example: content/pages/page_abc.json could store { id: 'page_abc', path: '/about', blocks: [...] }. Renaming /about would not rename the file. A slug-based filename is easier to browse manually but changes when the URL does.
Recommendation: Use permanent IDs for filenames and store editable paths/slugs inside. This separates content identity from public URLs.
Options: Permanent ID filenames; editable URL in the document / Readable slug/path filenames, with a permanent ID inside
Selected: Permanent ID filenames; editable URL in the document
Notes: 
```

## Question 36

```text
Round: QuineCMS — content and block contracts
Question: How should saved block data survive a block author changing its fields?
Context: A block instance could store { id: 'block_abc', type: 'core/hero', version: 1, props: {...} }. A later version might rename or reorganize those props. This is developer-owned compatibility, separate from the simple collection schema editor.
Recommendation: Version each block's saved data and let authors supply explicit migration functions. Preserve unsupported data and stop unsafe editing/publishing rather than silently dropping fields.
Options: Versioned data with explicit developer migration functions / Authors must keep old saved props compatible without migration functions / Keep old block implementations installed alongside new versions
Selected: Keep old block implementations installed alongside new versions
Notes: keep it simple here. old block implementations simply gets "deprecated" but still available. blocks would have a "version" selection field. users would need to manually migrate to the shape of the latest block by selecting the newer version of the block, in which newer unrecognized/renamed/irreconcilable fields would be empty, then manually fill them back in.
```

## Question 37

```text
Round: QuineCMS — content and block contracts
Question: What should the browser-facing block interface use?
Context: With framework adapters, most authors write a normal React/Svelte/Vue component. The adapter provides mount(host, props, context), update(props, context), and destroy(). Vanilla/custom blocks implement that lifecycle directly. The static build uses the shared rendering source where possible.
Recommendation: Use framework adapters with this small common lifecycle. This gives the editor a consistent way to update, reorder, and remove blocks without imposing its React framework on them.
Options: Framework adapters with mount/update/destroy / Require every block to expose a Web Component wrapper instead
Selected: Framework adapters with mount/update/destroy
Notes: 
```

## Question 38

```text
Round: QuineCMS — content and block contracts
Question: When should a published block load its interactive JavaScript?
Context: Public pages can contain built HTML before interactivity starts. An author can declare never for static blocks, visible for offscreen widgets, idle for low-priority behavior, or load for immediate interaction. The editor still mounts blocks immediately for live preview.
Recommendation: Let block authors declare the activation policy; static blocks need no client runtime, and interactive blocks load when appropriate.
Options: Author-declared never/visible/idle/load policy / Activate every interactive block as soon as the page loads
Selected: Author-declared never/visible/idle/load policy
Notes: 
```

## Question 39

```text
Round: QuineCMS — content and block contracts
Question: How should content refer to internal pages and uploaded media?
Context: A block can store a media ID whose record contains R2 URLs and image variants, or copy those URLs directly into its props. Navigation can similarly reference a page ID or its current path. The build resolves IDs to ordinary URLs in published HTML.
Recommendation: Use stable IDs for internal content/media and explicit URLs for external links. This keeps page renames and media metadata changes from requiring edits in every referring block.
Options: Stable IDs for internal references; URLs for external resources / Store paths and media URLs directly wherever they are used
Selected: Stable IDs for internal references; URLs for external resources
Notes: 
```
