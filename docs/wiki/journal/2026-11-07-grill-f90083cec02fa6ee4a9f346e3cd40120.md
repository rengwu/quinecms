## Question 18

```text
Round: Admin redesign, round 2: editor and navigation
Question: How should a page's blocks open for editing?
Description (Markdown source):
You chose stacks for nested items, so a block can open the same way. Both mockups show the split preview with the open block highlighted. Clicking a block in the preview could later open it the same way.
Recommendation: Open in a stack. All editing then works one way, the block list stays short enough to reorder, and the preview stays visible beside the stack. Expanding in place suits short blocks, but long blocks push the rest of the list out of view.
Options: Open in a stack over the editor / Expand in place in the block list
Selected: Open in a stack over the editor
Notes: 
Status: feedback
```

## Question 19

```text
Round: Admin redesign, round 2: editor and navigation
Question: When the preview is split, what should a stack cover?
Description (Markdown source):
Example: Home → Columns block → its Repairs item, two stacks deep. Each stack leaves a strip of the one below it visible. Click the strip, press Escape or use browser Back to close the top stack. Edits apply live, as they do now; a new item shows Create and Cancel. With the preview off or floating, a stack is at most 720px wide, anchored right, and a floating preview stays on top.
Recommendation: The editor column only, so the preview stays visible while you edit nested values.
```

## Question 20

```text
Round: Admin redesign, round 2: editor and navigation
Question: Should one navigation rule replace the current menus and sub-pages everywhere?
Description (Markdown source):
**Rule:** lists and records are screens, shown in the breadcrumbs. Anything inside a record, and every Add form, opens in a stack.

| Today | Proposed |
| --- | --- |
| Pages table → page editor | Screen: Pages / Home |
| Page → block (replaces the drawer, ← Back) | Stack (see the blocks question) |
| Object field, list item, reference (inner panel, ← Back) | Stack |
| Content → collection → entry list → entry | Collections / Journal (screen) → entry (screen) |
| Single collection (Contact details) | Opens straight to its editor screen |
| Schemas → collection → field | Schema screen → field in a stack |
| Media list → item | Media screen → item in a stack |
| Layouts table → layout settings with preview | Screen with the same preview modes |
| Settings sections | One Settings screen of rows |
| Add page, Add entry, Add field, Add block | Stack with Create and Cancel, then open the new record |
Recommendation: Yes. One rule is easier to learn, and it removes the drawer, the inner panels and their ← Back buttons.
Options: Yes, apply this rule everywhere / Mostly; changes in the notes
Selected: Yes, apply this rule everywhere

```

## Question 21

```text
Round: Admin redesign, round 2: editor and navigation
Question: Where should the preview controls go?
Description (Markdown source):
Splitting them up keeps each control near what it affects. **Showing** the preview is a layout toggle, like the sidebar toggle at the top left. **Docking or floating** it, switching **Desktop and Mobile**, and **closing** it belong to the preview itself. Its bar shows Float when split and Dock when floating. Below 800px there is no preview, so the toggle is hidden.

In the Statamic option, the side column moves under the main column beside a split preview, which pushes its Live preview button out of view.
Recommendation: A Preview toggle in the top bar, with the other controls on the preview’s own bar.
Options: Preview toggle in the top bar; Float, Dock, device and Close on the preview bar / Live preview button in the side column (Statamic); the same preview bar
Selected: Preview toggle in the top bar; Float, Dock, device and Close on the preview bar
```
