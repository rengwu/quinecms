## Question 77

```text
Round: Objects & relations · revised after CMS research
Question: How should object field groups be defined?
Description (Markdown source):
An **Address object** belongs to one Location. A **reusable Address definition** shares the street/city/postcode fields across collections, but each address still has its own values. Shared values, such as an Author biography reused by many articles, belong in a referenced entry.

[Sanity objects](https://www.sanity.io/docs/studio/object-type) and [Strapi components](https://docs.strapi.io/cms/features/content-type-builder#components) demonstrate reusable field structures. Inline groups are convenient for one-off shapes; named definitions keep repeated structures consistent. Editing a named definition would need an impact check across its uses.
Recommendation: Support both named reusable definitions and inline groups. Reuse common structures without forcing every small group into a library.
Options: Both named definitions and inline groups / Named reusable definitions only / Inline groups only
Selected: Both named definitions and inline groups
```

## Question 78

```text
Round: Objects & relations · revised after CMS research
Question: Should objects and lists be able to nest inside one another?
Description (Markdown source):
An Event might have a list of Sessions; each Session could contain a time and a list of Speaker references. A Location might contain a Contact object with several phone numbers.

[Keystatic's object example](https://keystatic.com/docs/fields/object) nests an array of relationships inside an object. Nesting increases modeling freedom and makes editor navigation more important. Each deeper editor would open its own level, following our current navigation direction.

This question is about ordinary nesting. Exact depth limits and self-referential type definitions are separate engineering choices; recursive schemas do not necessarily mean infinite content.
Recommendation: Allow nested objects and lists. A one-level restriction would exclude ordinary event, directory and product structures.
Options: Allow nested objects and lists / Keep objects and lists to one level
Selected: Keep objects and lists to one level
Notes: 
```

## Question 79

```text
Round: Objects & relations · revised after CMS research
Question: Can a relation field allow entries from several collections?
Description (Markdown source):
An Article.author field would normally allow **Authors** only. A Homepage.featured field might allow **Articles or Events**, preserving one editorial order. The number of linked entries is a separate choice from their allowed collection types.

[Payload relationships](https://payloadcms.com/docs/fields/relationship) and [Sanity references](https://www.sanity.io/docs/studio/reference-type) support multiple allowed target types. This revises my earlier single-collection-only recommendation.

The tradeoff: an Article and an Event may expose different fields. Their binding and rendering must handle each type explicitly, or use a deliberately defined common shape.
Recommendation: Allow one or several explicitly selected collections, defaulting to one. This supports mixed editorial selections while keeping ordinary fields simple.
Options: Allow an explicit set of one or more collections / Limit every relation field to one collection
Selected: Limit every relation field to one collection
Notes: 
```

## Question 80

```text
Round: Objects & relations · revised after CMS research
Question: Should a list field support different declared object shapes?
Description (Markdown source):
A list of FAQ items repeats one shape: Question + Answer. An article body may need a sequence such as **Quote → Image → Callout**, with different fields for each item type.

[Strapi dynamic zones](https://docs.strapi.io/cms/features/content-type-builder#dynamic-zones) and [Payload Blocks](https://payloadcms.com/docs/fields/blocks) cover this second case. Ordinary nesting alone does not provide it.

Our schema would explicitly allow the available shapes, and the template would control how each renders. This can be an entry field without giving every entry an unrestricted page layout. It adds a type picker and a rendering branch for each allowed shape.
Recommendation: Allow mixed shapes when explicitly configured for the list. Keep one-shape lists as the simpler default.
Options: Support explicitly allowed object variants / Use one object shape per list for now
Selected: Use one object shape per list for now
Notes: 
```

## Question 81

```text
Round: Objects & relations · revised after CMS research
Question: What should happen when an editor deletes an entry that other content references?
Description (Markdown source):
An Author is referenced by five Articles. Deleting the Author affects all five. [Sanity distinguishes strong references, which block deletion, from weak references, which permit missing targets](https://www.sanity.io/docs/studio/reference-type).

Three possible policies:

- **Block:** show the incoming uses; remove or reassign those links before deletion.
- **Clear together:** delete the Author and clear incoming links in one draft change. Required author fields then prevent publication until repaired.
- **Allow missing targets:** keep the references, show warnings, and let rendering resolve them as empty.

An optional field may be blank; that is separate from allowing a stored reference to point to a missing entry. No option automatically deletes the referring Articles.
Recommendation: Block deletion while referenced, with a useful incoming-usage list and a repair path. This keeps shared content changes explicit.
Options: Block until incoming links are removed or reassigned / Delete and clear incoming links together / Allow missing targets with warnings and empty rendering
Selected: Block until incoming links are removed or reassigned
Notes: 
```
