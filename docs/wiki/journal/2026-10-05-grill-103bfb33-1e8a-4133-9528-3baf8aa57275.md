## Question 25

```text
Round: QuineCMS — technical foundations
Question: Which foundation should build the public site?
Context: Both choices produce static HTML and keep the admin app static. Astro already integrates multiple UI frameworks. A custom Vite-based generator would make us own routing, prerendering, and framework integration ourselves.
Recommendation: Astro with TypeScript: use its static build and framework integrations, while keeping our content format and block definitions independent where practical.
```

## Question 27

```text
Round: QuineCMS — technical foundations
Question: What should the source content files use?
Context: These files hold page metadata, ordered block instances, field values, and collection definitions. The format must survive browser editing and remain understandable in Git.
Recommendation: Formatted JSON. It directly represents the editor's structured data and needs no extra parser or executable content.
Options: JSON for structured content and definitions / YAML for structured content and definitions / Markdown with frontmatter and an embedded block representation
Selected: JSON for structured content and definitions
Notes: 
```

## Question 28

```text
Round: QuineCMS — technical foundations
Question: How should content be divided into files?
Context: Many small files make individual changes easier to review and reduce unrelated edits touching the same file. Large aggregate files are easier to fetch but combine more changes.
Recommendation: One file per page or entry, one per collection definition, and separate site settings/media records. Save related file changes together in one commit.
Options: Separate files per page, entry, and definition / One aggregate file per collection, plus pages/settings files / One file containing the whole site's content and definitions
Selected: Separate files per page, entry, and definition
Notes: 
```

## Question 29

```text
Round: QuineCMS — technical foundations
Question: What should a field schema look like?
Context: The portal must save schemas as data. A small model could look like { key: 'title', type: 'text', required: true }. JSON Schema is a broader standard for validating data; form widgets and layout still need extra metadata.
Recommendation: Use a small declarative field model covering the agreed field types, interpreted by the editor and build. Keep it serializable and versioned.
Options: A small purpose-built field model / A supported subset of JSON Schema plus editor UI metadata
Selected: A small purpose-built field model
Notes: 
```

## Question 30

```text
Round: QuineCMS — technical foundations
Question: What rendering contract should a block author follow for published pages and live preview?
Context: Both paths must show the same content and design. A reusable React/Svelte/Vue component can often serve both, but a build-only template cannot itself rerender unsaved changes in the browser.
Recommendation: Share rendering source by default. Allow separate build/preview implementations when necessary, with checks that they stay equivalent.
Options: Shared rendering source by default; separate implementations require parity checks / Require one reusable rendering source for every block / Treat build and preview as separate implementations for every block
Selected: Shared rendering source by default; separate implementations require parity checks
Notes: my suggestion: all libraries used by authored blocks (that are possibly shared) (e.g. react@18, svelte@5, react-hook-form@7.8, @base-ui/react@1.8, etc.) should have their (minified, if possible) registered vendor files located in a statically hosted  location, and loaded from there. this way, we don't have to load more than 1 different versions of react, or more than 1 different versions of svelte, if possible. keeping the asset loading lean
```

## Question 31

```text
Round: QuineCMS — technical foundations
Question: Should the preview share the editor's document or live in an iframe?
Context: A shared document can reuse the editor's live framework runtime, but requires scoped styles. An iframe isolates the preview's CSS and viewport; its runtime is separate even if downloads are cached, relaxing runtime deduplication inside the admin view. Public pages can still deduplicate normally.
Recommendation: Use one document with scoped editor/block CSS to preserve runtime sharing. Treat CSS isolation as part of the block contract.
Options: One document; scope styles and share runtimes / A preview iframe; accept separate runtime instances in the admin view
Selected: One document; scope styles and share runtimes
Notes: 
```

## Question 32

```text
Round: QuineCMS — technical foundations
Question: Can block authors add custom field controls to the editor?
Context: Built-in controls cover ordinary text, choices, images, and similar values. A custom widget could provide a special color palette, chart-data editor, or other block-specific control.
Recommendation: Provide built-in controls plus a small optional custom-widget interface. Custom widgets use the editor's selected framework; the block's renderer remains framework-independent.
Options: Built-in controls plus optional custom widgets / Built-in controls only for the first version
Selected: Built-in controls plus optional custom widgets
```
