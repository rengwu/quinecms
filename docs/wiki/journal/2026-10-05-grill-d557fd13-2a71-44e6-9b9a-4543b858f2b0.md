## Question 48

```text
Round: Generic pages and collections
Question: If a collection has no generic page assigned, what should happen to its entries on the public website?
Context:
Recommendation: Keep the entries available as data, but generate no individual entry pages. Layout assignment then has a clear purpose.
Options: Data only; no individual entry pages / Generate a default entry page from its fields / Require a generic page before publishing any collection entries
Selected: Data only; no individual entry pages
Notes: yeah make it data only. i could have a collection of links with no generic page, named "footer links", and then i use it in the site footer (in the future, out of scope for now).
```

## Question 52

```text
Round: Generic pages and collections
Question: If a generic block binds to a field name that does not exist in an assigned schema, or the value type is incompatible, how should publishing behave?
Context:
Recommendation: Allow the incomplete draft, but prevent publishing until the binding is fixed. This catches broken connections before they become public.
Options: Allow draft saving; block publishing until fixed / Publish using the block field's fixed value as a fallback / Publish with the affected block field empty
Selected: Allow draft saving; block publishing until fixed
Notes:
```

## Question 53

```text
Round: Generic pages and collections
Question: If the bound schema field exists and is optional, but an entry leaves it empty, what should the generic block field display?
Context:
Recommendation: Use the block field's fixed value when one is set; otherwise leave it empty. This supports a shared fallback without changing entry data.
Options: Use the block field's fixed value, otherwise empty / Always leave the bound field empty / Require every bound field to have an entry value before publishing
Selected: Use the block field's fixed value, otherwise empty

```
