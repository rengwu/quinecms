# One fixed development login

The user requests that `admin@example.com` / `asdf1234` always work in development,
and clarifies that there is one shared account, dashboard and set of content.
DEC-152 implements that directly, without another interview or account model.

The admin page encrypts its development payload using that fixed pair, replacing
any environment credentials. Astro's command sets the development flag; build
and preview retain the configured production pair and missing-credential failure.
The encryption format, login form, dashboard and content/recovery data are unchanged.
README, example instructions and runner output now show the correct dev login.
The example's isolated static build retains its existing public test credentials.

Regression tests decrypt actual dev HTTP responses with absent and different `.env`
credentials, reject the other pair in dev, and reject the dev pair against production
fixture output. The existing missing-production-credentials check also passes.
Both currently running dev editors (4322 and Quine on 4323) were fetched and their
actual encrypted responses decrypted successfully with the fixed pair. Refresh the
page before using the new login. No client content or `.env` file was changed.

An initial attempt used `import.meta.env.DEV`; the regression check caught that a
build inheriting `NODE_ENV=test` accepted the dev pair. This was corrected by deriving
`LEAN_DEV_SERVER` from Astro's command before the passing verification. The new dev
HTTP harness also needed to remove its inherited `VITEST` marker because Astro
intentionally skips its server middleware under that marker.

`pnpm verify` passed: zero type errors/warnings, 204 tests in 30 files, production
build and artifact checks. Native browser automation remained unavailable.
