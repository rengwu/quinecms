## Question 20

```text
Round: QuineCMS — round four
Question: How should the editor get permission to upload media to R2?
Context: The bucket address can come from environment variables. But if a build embeds R2 write credentials in the static site, visitors can extract them despite the login gate. Keeping environment credentials secret requires a separate service to authorize uploads.
Recommendation: To preserve the entirely static app, let the editor supply bucket-scoped R2 credentials at runtime and retain them for the tab session, like the GitHub token.
Options: Supply R2 credentials in the editor; keep the app entirely static / Allow a small authenticated serverless upload helper that keeps R2 credentials in server-side environment variables / Upload media outside the editor and paste its URL; no upload credentials in the app
Selected: Supply R2 credentials in the editor; keep the app entirely static
Notes: 
```

## Question 21

```text
Round: QuineCMS — round four
Question: How much should the first collection schema editor support?
Context: You chose both developer-defined schemas and collections created through the portal. This question sets the portal's initial field-editing scope; entry bodies still use blocks.
Recommendation: Start with basic fields and safe changes: add fields, edit labels/defaults, and avoid destructive changes to populated fields. This keeps existing content usable without a migration interface.
Options: Basic text, number, date, toggle, select, and media fields; safe changes only / Also support nested/repeating fields and links between collections / Also support changing populated field types and migrating existing content
```

```text
Round: QuineCMS — round four
Question: How should a collection created in the portal appear on the public site?
Context: For example, a new Recipes collection needs a listing and individual recipe URLs, unless it is only used as data inside other pages.
```

## Question 23

```text
Round: QuineCMS — round four
Question: Should the media uploader just store files, or also process them?
Context: R2 stores files. Image resizing and video transcoding would be additional behavior, with extra processing and failure cases.
Recommendation: Start with original-file uploads for common images, documents, audio, and video, with configurable size/type limits. Add processing separately when needed.
Options: Upload original files only / Also resize and compress images automatically / Also process video/audio for playback
Selected: Also resize and compress images automatically
Notes: uploading a large enough image would generate an image set that is optimized for web, light compression would be applied as well. somewhat like how next.js's Image component does optimization. but only do the simplest and leanest way here, don't overengineer, only apply simpler methods.
```

## Question 24

```text
Round: QuineCMS — round four
Question: May uploaded media be accessible at its direct URL before Publish?
Context: In a public R2 asset bucket, someone with an uploaded file's URL can access it even while the page referencing it is still a draft. The draft page itself does not become published.
Recommendation: Allow public media URLs immediately for a simpler static workflow. Choose private drafts only if unpublished media must be confidential.
Options: Yes; media URLs may work immediately, while pages remain drafts / No; media must remain private until the content is published
Selected: Yes; media URLs may work immediately, while pages remain drafts
```
