## Question 83

```text
Round: Collections & schemas · content models
Question: Should we support single-record content such as a Company Profile?
Description (Markdown source):
Articles need many entries. A Company Profile may need just one centrally managed record containing the company name, description and contact details.

A **single-entry mode** would open that record's editor directly and prevent additional entries. Its schema would belong to that content model, following your last choice. This shares one record's values; a reusable object definition only shares field structure.

The simpler alternative is ordinary collections only, with the editor manually maintaining one entry when needed. Adding a single-entry mode introduces creation/deletion and mode-switching behavior to define next.
Recommendation: Support a single-entry mode for shared content that should exist only once. It gives editors a clear home for that content.
Options: Support single-entry and ordinary collection modes / Keep ordinary collections only
Selected: Support single-entry and ordinary collection modes

```

## Question 84

```text
Round: Collections & schemas · content models
Question: Should data-only collections require URL prefixes and entry slugs?
Description (Markdown source):
Authors might supply names and biographies to Articles without having public author pages. We already support collections without entry routes. The remaining choice is whether editors must still provide URL metadata for them.

With route-specific requirements, data-only entries need stable IDs and useful display labels, but no URL prefix or slug. Assigning a generic page would require valid routing metadata before publication. Previously configured URL values could remain stored when routes are disabled.

Keeping URL metadata on every collection prepares it for future pages, but adds fields with no current public use.
Recommendation: Require URL prefixes and slugs only when the collection generates entry pages. Keep content identity independent of URLs.
Options: Require URL metadata only for routed collections / Require URL metadata for all collections
Selected: Require URL metadata only for routed collections
Notes: 
```

## Question 85

```text
Round: Collections & schemas · content models
Question: Should a relation field support selecting one entry or multiple entries?
Description (Markdown source):
An Article.author field might select one Author. Article.coAuthors could select several Authors, and Article.categories could select several Categories.

Every field would still target exactly one collection, as you already chose. The new choice is how many entries it can select from that collection. With single references only, multi-author credits or category membership need another modeling pattern.

This question does not yet settle ordering, duplicate selections, reverse views, or the treatment of multiple references inside an object or list row.
Recommendation: Make one or multiple selections configurable per relation field. Both are common content structures and use the same target-selection model.
Options: Support one or multiple entries per field / Support one entry per field only
Selected: Support one or multiple entries per field

```
