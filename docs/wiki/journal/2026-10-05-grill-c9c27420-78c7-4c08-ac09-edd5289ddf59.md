## Question 15

```text
Round: QuineCMS — round three
Question: How long should the editor remember your GitHub token?
Context: Private repository drafts need the token when loading, as well as saving. Browser storage makes repeat visits easier but retains a credential on that device.
Recommendation: Keep it in memory while the editor is open; ask again after a reload. This avoids storing the token on disk through the app.
Options: In memory only; enter it again after reloading / Keep it for the browser tab's session, including reloads / Remember it on this device until I sign out
Selected: Keep it for the browser tab's session, including reloads

```

## Question 16

```text
Round: QuineCMS — round three
Question: When you say the portal saves schema changes, what should users be able to change?
Context: A schema defines fields such as a post's title, date, and category. Editing those definitions is different from editing a post's values. New block rendering code is still installed by a developer, as agreed.
Recommendation: Start with developer-defined schemas and let the portal edit their content. Add a visual schema editor only if users need to create their own content models.
Options: Developers define schemas; the portal edits content values only / Users can create collections and change their fields in the portal / Users can edit collection schemas and existing blocks' field definitions in the portal
Selected: Users can create collections and change their fields in the portal
Notes: 1 and 2
```

## Question 17

```text
Round: QuineCMS — round three
Question: How much simultaneous editing should the first release support?
Context: Everyone's saved drafts accumulate before Publish. If another edit has changed the same content, an older save must not silently overwrite it.
Recommendation: Use one shared draft branch with stale-save protection. Preserve local edits and ask the editor to refresh and reapply conflicting changes; add richer collaboration later.
Options: Shared drafts with stale-save protection; manual reapplication is acceptable / Parallel editing with an in-app interface to compare and resolve conflicts / Live collaborative editing, with other people's changes appearing immediately
Selected: Shared drafts with stale-save protection; manual reapplication is acceptable
Notes: keep it lean and simple to understand. we dont want conflicts, or any problems that a layman non-technical person might not understand.
```

## Question 18

```text
Round: QuineCMS — round three
Question: Which media should users be able to upload in the first release?
Context: Uploaded files will be committed to the same repository. Supporting large audio or video files substantially increases repository size and upload work.
Recommendation: Support images and downloadable documents first, with validation and size limits.
Options: Images only / Images and downloadable documents / Also upload audio and video files
Selected: Something else
Notes: i'm planning to use cloudflare R2 for media. accept cloudflare r2 tokens in env vars. and the github-saved content just points to media hosted in the r2 bucket.
```

## Question 19

```text
Round: QuineCMS — round three
Question: How should site-wide styling work alongside each block's own design?
Context: You want independently designed blocks. Shared colors, fonts, and spacing can still make a site consistent without removing block-specific controls.
Recommendation: Provide site-wide defaults that blocks can inherit, with each block exposing its own overrides and keeping its CSS scoped.
Options: Shared site defaults with block-specific overrides / Every block manages its own styling independently / All blocks must follow a single site-wide theme
Selected: Shared site defaults with block-specific overrides
Notes: there are site-wide switches, yes, like dark/light mode and other more general styles and settings. but mostly, each block will manage its own styling independently. the site-wide switches are just global variables which the blocks may or may not listen or adhere to.
```
