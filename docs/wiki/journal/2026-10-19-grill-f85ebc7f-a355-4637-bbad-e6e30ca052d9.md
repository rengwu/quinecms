## Question 6

```text
Round: QuineCMS internationalization — remaining decisions
Question: What makes a language copy eligible for public output?
Description (Markdown source):
We already agreed on whole-item fallback and incomplete drafts. This decision defines when a translation stops being treated as unavailable. Eligibility applies at the next Publish/build; marking a translation ready does not publish the site by itself.
Recommendation: Use an explicit Ready control for each item's language copy, with required-field validation. Valid fields alone cannot tell us whether an editor has finished translating.
Options: An editor marks the language copy Ready; it must also pass validation / A language copy becomes eligible automatically when its required fields are valid
Selected: A language copy becomes eligible automatically when its required fields are valid

```

## Question 7

```text
Round: QuineCMS internationalization — remaining decisions
Question: When the main-language text changes, what happens to an already usable translation?
Description (Markdown source):
For example, the English product description changes after its Indonesian copy was completed. This question concerns source text edits. A removed shared section or a schema change that makes content invalid still has to obey structural validation.
Recommendation: Keep the existing translation eligible and flag it as needing review. This prevents a small English edit from unexpectedly replacing Indonesian content with English, while showing editors what needs attention. Under this choice, a review warning alone would not block strict publication.
Options: Keep it eligible and show a Needs review warning / Treat it as unavailable until reviewed; fallback or strict rejection then applies / Keep it eligible without tracking whether the source changed
Selected: Keep it eligible without tracking whether the source changed
Notes: simplest solution here. refer to jstack's rule-lean
```

## Question 8

```text
Round: QuineCMS internationalization — remaining decisions
Question: Which visitor-facing content should the first i18n release cover?
Description (Markdown source):
Besides page sections and collection entries, visitors see shared navigation, footer labels and layout copy. Search-engine descriptions and image descriptions can also contain language-specific text. This concerns website content, not translating the QuineCMS admin interface.
Recommendation: Cover all visitor-facing content, including shared layout copy and metadata wherever those fields exist. Otherwise a translated page can still have an untranslated shell.
Options: Pages, entries, shared layout/navigation copy, and visitor-facing metadata / Pages and entries first; defer shared layout copy and metadata
Selected: Pages, entries, shared layout/navigation copy, and visitor-facing metadata
Notes: 
```

## Question 9

```text
Round: QuineCMS internationalization — remaining decisions
Question: How should we decide which field values can vary by language?
Description (Markdown source):
A product name may need translation while its size, date or product reference may need to stay shared. Images and external links can also differ between markets. Shared page sections, their order and templates remain fixed by our earlier decision. A deliberately shared field is common data, not per-field fallback from an incomplete translation.
Recommendation: Make localization an explicit field setting, shared by default. The person defining the schema or block/layout fields chooses what can vary; content editors fill those language-specific values.
Options: Choose localization per field; fields are shared by default / Copy every editable content value into each language version / Automatically localize text fields; keep all other field types shared
Selected: Choose localization per field; fields are shared by default
Notes: 
```

## Question 10

```text
Round: QuineCMS internationalization — remaining decisions
Question: Should page paths and entry slugs be translatable in the first release?
Description (Markdown source):
The main language is already unprefixed and secondary languages are prefixed. With shared slugs, an Indonesian product keeps /id/product/face-wash. Localized paths could use /id/produk/pembersih-wajah. Internal references should continue to identify the same item in either case.
Recommendation: Keep paths and slugs shared for the first release, adding only the language prefix. This keeps the small proof focused; localized paths can be a later capability.
Options: Share paths and slugs; add only the language prefix / Support language-specific paths and slugs in the first release
Selected: Share paths and slugs; add only the language prefix
Notes: 
```

## Question 11

```text
Round: QuineCMS internationalization — remaining decisions
Question: Where should people manage the site's languages and strict-versus-fallback policy?
Description (Markdown source):
These are site-wide content settings: enable/disable i18n, select the main language, choose additional languages and select the completeness policy. They are separate from deployment credentials. Field localization remains part of schema/design definition.
Recommendation: Expose these controls in the portal's Settings and save/publish them with site content, so the maintainer does not need to edit repository configuration for routine language management.
Options: Portal Settings, saved and published with site content / Developer-managed site configuration only
Selected: Portal Settings, saved and published with site content
```

## Question 12

```text
Round: QuineCMS internationalization — remaining decisions
Question: Should the first release support changing the main language after translations exist?
Description (Markdown source):
The main language supplies fallback content and owns the unprefixed URLs. Switching it therefore changes more than a display preference. Disabling and re-enabling i18n does not by itself require changing the main language; retaining translations while disabled remains the proposed non-destructive behavior.
Recommendation: Fix the main language once translations exist and defer switching to a deliberate migration feature. This avoids adding content promotion and URL migration to the initial i18n scope.
Options: Fix the main language once translations exist; defer migration support / Provide a guided main-language switch in the first release
Selected: Fix the main language once translations exist; defer migration support
Notes: 
```
