## Question 8

```text
Round: lean-sitebuilder — round two
Question: What should the admin login protect?
Context: A password checked entirely in a static page can be bypassed. An environment variable does not change that. GitHub can still enforce access to the repository through the supplied token.
Recommendation: Use the configured password as a convenience gate, with GitHub enforcing repository access. This keeps the editor entirely static.
Options: A convenience gate is enough; GitHub controls repository access / The admin page itself must be protected by hosting-provider access control
Selected: A convenience gate is enough; GitHub controls repository access
Notes: 
```

## Question 9

```text
Round: lean-sitebuilder — round two
Question: What repository visibility must a deployed site support?
Context: This refers to each site's repository. Public repositories expose source and draft branches. Private repositories also need authorization to read draft content, before saving anything.
Recommendation: Start with private site repositories so unpublished content stays private.
Options: Private repositories only / Public repositories only; drafts may be visible / Both private and public repositories
Selected: Both private and public repositories
Notes: i usually deploy to netlify, which supports deployment on private repo branch pushes. i think theres no need to worry about this.
```

## Question 10

```text
Round: lean-sitebuilder — round two
Question: Who should provide the GitHub token used by an editor?
Context: This determines whether clients need their own GitHub account and who can revoke access. Do not enter an actual token here.
Recommendation: Each editor uses their own GitHub account and token, so access can be revoked individually. The exact token setup must support their repository role.
Options: Each editor provides their own GitHub token / The site owner supplies a token for editors to use / Only a technical owner uses the token to save and publish
Selected: Each editor provides their own GitHub token
Notes: 
```

## Question 11

```text
Round: lean-sitebuilder — round two
Question: Which deployment setup should we support first?
Context: Publishing merges drafts into main; a build must then deploy the static output. GitHub Pages hosting from a private repository requires an eligible account plan.
Recommendation: Provide GitHub Actions and GitHub Pages as the reference setup, while keeping the output portable to other static hosts.
Options: GitHub Actions builds and deploys to GitHub Pages / An existing Git-connected host deploys main; name it in Notes / Provide build output only; the owner configures deployment
Selected: (notes only)
Notes: the site builder pushes content and schema changes to github with a SDK client. publish merges to main. when main is pushed, my netlify deployment will detect that and deploy it on its own, which you dont need to worry much about
```

## Question 13

```text
Round: lean-sitebuilder — round two
Question: Can we require block authors to provide a browser-compatible preview?
Context: The editor must render unsaved changes immediately. A block that can only render during a build cannot do this without a separate preview implementation.
Recommendation: Require a browser preview for every block, sharing rendering logic with the published version where possible.
Options: Yes; every block must support immediate browser preview / Allow build-only blocks with a placeholder while editing
Selected: Yes; every block must support immediate browser preview
Notes: 
```

```text

Question: How should new block types become available in the editor?
Context: This concerns installing a new block type, not adding another instance of an already-installed block to a page.
Recommendation: A developer adds and registers block code, then rebuilds. This lets the build compile frameworks and share compatible dependencies.
Options: Developer installs and registers blocks in the repo, then rebuilds / Editors must be able to install new block types through the portal
```
